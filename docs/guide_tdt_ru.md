# Табличные тесты в Go: тестируем yak8sui

> **Для кого это?** Для тех, кто только начинает изучать Go и хочет понять, как
> в этом языке устроено тестирование — без сторонних фреймворков, без библиотек
> ассертов, только штатный инструментарий. В качестве подопытных возьмём две
> крошечные функции из `yak8sui` и объясним *почему* написана каждая строка, а
> не только *что* она делает.

Если вы читали [основное руководство](guide_ru.md), то знаете, что проект
разделён на слой **данных** (`pkg/k8s`) и слой **UI** (`pkg/ui`). Там мимоходом
упоминалось, что чистые данные «можно тестировать без терминала». Этот документ
выполняет то обещание: он добавляет в проект **первые два теста** и учит идиоме,
на которую опирается любая Go-кодовая база, — **табличному тесту (table-driven
test)**.

## 1. Что значит «тестирование» в Go

Придя из других языков, вы, возможно, ожидаете `pip install` или `npm add`
какого-нибудь тест-фреймворка (JUnit, pytest, Jest, Mocha…). В Go **ставить
нечего**. Тестирование встроено в сам язык и инструментарий:

- В стандартной библиотеке есть пакет **`testing`**.
- Команда **`go test`** находит и запускает ваши тесты.
- **Нет хелперов-ассертов** вроде `assertEquals`. Значения сравнивают обычным
  `if`, а о провале сообщают через `t.Errorf`. Поначалу это кажется скудным, но
  зато тестовый код — это *просто код на Go*, никакого нового DSL учить не надо.

Эта философия — «меньше магии, больше обычного кода» — та же, что вы встретили в
основном руководстве при обработке ошибок (`if err != nil` вместо исключений).

## 2. Правила: имена файлов, пакетов, функций

Инструментарий Go находит тесты по **соглашению**, а не по конфигурации. Три
правила:

### Правило 1 — файл должен оканчиваться на `_test.go`

Наши файлы — `pkg/ui/colors_test.go` и `pkg/ui/app_test.go`. Суффикс `_test.go`
особый: такие файлы компилируются **только** при `go test` и **исключаются** из
обычного `go build`. То есть тестовый код никогда не попадает в итоговый бинарник.

### Правило 2 — тест-функция имеет вид `func TestXxx(t *testing.T)`

- Имя должно начинаться с `Test`, за которым идёт заглавная буква
  (`TestStatusColor`, а не `Teststatuscolor`).
- Принимает ровно один аргумент: `t *testing.T`. Этот `t` — ваша «рукоятка» к
  тест-раннеру: через него вызывают `t.Run(...)` для подтестов и `t.Errorf(...)`
  для фиксации провала.

### Правило 3 — выбор пакета: «белый ящик» против «чёрного ящика»

Файл `_test.go` может объявлять один из двух пакетов:

| Объявление | Название | Видит неэкспортируемые (строчные) имена? | Как называют |
|---|---|---|---|
| `package ui` | внутренний тест | **Да** | white-box |
| `package ui_test` | внешний тест | Нет — только публичный API | black-box |

Мы выбрали **`package ui`** (white-box) для обоих файлов. Почему? Потому что
`statusColor` — **неэкспортируемая** функция (строчная `s`): снаружи пакета её
попросту нельзя назвать по имени. Раз мы хотим тестировать её напрямую, тест
обязан жить *внутри* `package ui`. Метод `ScreenType.String()` экспортируемый и
мог бы быть в любом из вариантов, но держать оба файла в `package ui` — проще и
единообразнее.

> **Замечание для обучения:** раздел 5.1 основного руководства объяснял, что
> регистр буквы управляет видимостью (`App` — публичный, `namespace` —
> приватный). Именно это правило и вынуждает выбрать здесь white-box — отличный
> пример того, как правило языка влечёт конкретное следствие в коде.

## 3. Что мы тестируем и почему именно эти две функции

Мы намеренно взяли две **самые чистые** функции в проекте:

**`statusColor`** — в `pkg/ui/colors.go`:

```go
func statusColor(status string) tcell.Color {
    switch status {
    case "Running", "Succeeded":
        return tcell.ColorGreen
    case "Pending":
        return tcell.ColorYellow
    default:
        return tcell.ColorRed
    }
}
```

**`ScreenType.String()`** — в `pkg/ui/app.go`:

```go
func (s ScreenType) String() string {
    switch s {
    case ScreenPods:
        return "Pods"
    case ScreenDeployments:
        return "Deployments"
    default:
        return "Unknown"
    }
}
```

Идеальными первыми тестами их делает то, что это **чистые функции (pure
functions)**:

- **Одинаковый вход → одинаковый выход, всегда.** Никакой случайности, часов или
  глобального состояния.
- **Нет побочных эффектов.** Они не трогают сеть, файловую систему или терминал.
  Сравните с `newPodsTable` или `k8s.ListPods`, которым нужен живой кластер
  Kubernetes и экран `tview`: тестировать *их* — значит городить дополнительную
  оснастку (интерфейсы и фейки), которую мы сейчас сознательно пропускаем.
- **Нет подготовки (setup).** Вызвали функцию — проверили результат. Всё.

Чистая функция — это «hello world» тестирования: нечего мокать, нечего убирать
за собой. Освоив приём здесь, вы примените его где угодно.

> **Важное свойство: эти тесты полностью аддитивны.** Мы написали два новых
> файла `_test.go` и не изменили **ни одной** строки существующего кода. Файлы
> `colors.go` и `app.go` побайтово те же, что и раньше. Это максимально
> безопасное изменение — полностью обратимое удалением двух тест-файлов.

## 4. Анатомия табличного теста

**Табличный тест** описывает каждый сценарий как **строку данных** в срезе, а
затем в цикле прогоняет по строкам одну и ту же проверку. Эта форма настолько
распространена в Go, что вы будете мгновенно узнавать её в любом реальном коде:

```go
func TestSomething(t *testing.T) {
    // 1. ТАБЛИЦА: срез анонимных структур, по одной строке на сценарий.
    cases := []struct {
        name string // что проверяет эта строка
        in   InputType
        want OutputType
    }{
        {name: "первый сценарий", in: ..., want: ...},
        {name: "второй сценарий", in: ..., want: ...},
    }

    // 2. ЦИКЛ: пройтись по всем строкам.
    for _, tc := range cases {
        // 3. ПОДТЕСТ: t.Run изолирует каждую строку под своим именем.
        t.Run(tc.name, func(t *testing.T) {
            got := Something(tc.in)
            if got != tc.want {
                t.Errorf("Something(%v) = %v, want %v", tc.in, got, tc.want)
            }
        })
    }
}
```

Три вещи, которые нужно усвоить:

1. **Таблица** — это `[]struct{...}{...}`, *анонимный* тип структуры, объявленный
   и заполненный прямо на месте. В основном руководстве (раздел 2.4) вводились
   именованные структуры вроде `PodInfo`; здесь у структуры нет имени, ведь она
   существует только чтобы хранить строки теста. У каждой строки по соглашению
   есть `name`, входные данные и ожидаемое `want`.
2. **Цикл** обходит строки через `for _, tc := range cases` (`tc` = «test case»,
   тестовый случай).
3. **`t.Run(name, func)`** создаёт **подтест (subtest)** — именованный, отдельно
   отчитывающийся дочерний тест. Если упадёт строка 4, Go точно скажет, какая
   именно, по имени, а остальные строки всё равно отработают.

> **О переменной цикла:** раздел «Подводные камни» основного руководства
> предупреждал о захвате переменной цикла `for` в замыкании. Здесь ту же
> переменную `tc` захватывает замыкание `t.Run`. На Go 1.22+ (в проекте — 1.26)
> каждая итерация получает свежую `tc`, поэтому всё безопасно и строка `tc := tc`
> не нужна. На старых версиях Go вы добавили бы `tc := tc` внутри цикла.

## 5. Наши тесты, строка за строкой

### 5.1 `colors_test.go`

```go
package ui

import (
    "testing"

    "github.com/gdamore/tcell/v2"
)

func TestStatusColor(t *testing.T) {
    cases := []struct {
        name   string      // человекочитаемое описание, видно в выводе теста
        status string      // вход для statusColor
        want   tcell.Color // цвет, который мы ожидаем получить
    }{
        {name: "running is green", status: "Running", want: tcell.ColorGreen},
        {name: "succeeded is green", status: "Succeeded", want: tcell.ColorGreen},
        {name: "pending is yellow", status: "Pending", want: tcell.ColorYellow},
        {name: "failed falls through to red", status: "Failed", want: tcell.ColorRed},
        {name: "unknown status is red", status: "CrashLoopBackOff", want: tcell.ColorRed},
        {name: "empty string is red", status: "", want: tcell.ColorRed},
    }

    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            got := statusColor(tc.status)
            if got != tc.want {
                t.Errorf("statusColor(%q) = %v, want %v", tc.status, got, tc.want)
            }
        })
    }
}
```

Читаем:

- **`package ui`** — white-box, чтобы можно было вызвать неэкспортируемую
  `statusColor`.
- **Импортируем `tcell`**, потому что *ожидаемые* значения — это константы
  `tcell.Color` (`tcell.ColorGreen`, …). Тест говорит на том же языке, что и
  тестируемая функция.
- **В таблице шесть строк**, покрывающих все три ветки: оба значения `case`,
  дающие зелёный, случай с жёлтым и — что важно — **три** входа, задействующих
  ветку `default` (`"Failed"`, выдуманный статус и `""`).
- **`got := statusColor(tc.status)`** запускает настоящую функцию.
- **`if got != tc.want { t.Errorf(...) }`** — это и есть весь «ассерт». Никакой
  библиотеки — просто сравнение. `t.Errorf` фиксирует провал *и позволяет тесту
  продолжиться* (в отличие от `t.Fatalf`, который немедленно останавливает
  текущий подтест).
- **Глаголы форматирования** важны для читаемых сообщений: `%q` заключает строку
  в кавычки (поэтому пустой вход печатается как `""`, а не пустотой), а `%v`
  печатает значение цвета в виде по умолчанию.

### 5.2 `app_test.go`

```go
package ui

import "testing"

func TestScreenTypeString(t *testing.T) {
    cases := []struct {
        name   string
        screen ScreenType
        want   string
    }{
        {name: "pods screen", screen: ScreenPods, want: "Pods"},
        {name: "deployments screen", screen: ScreenDeployments, want: "Deployments"},
        {name: "out-of-range value", screen: ScreenType(99), want: "Unknown"},
    }

    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            got := tc.screen.String()
            if got != tc.want {
                t.Errorf("ScreenType(%d).String() = %q, want %q", tc.screen, got, tc.want)
            }
        })
    }
}
```

Два момента стоит отметить:

- **`tc.screen.String()`** — мы тестируем **метод** типа, поэтому вызываем его на
  значении (`tc.screen`), а не как отдельную функцию. `ScreenType` — по сути
  обычный `int` (см. enum на `iota` в основном руководстве, раздел 4.2), и
  `String()` как раз превращает `ScreenPods` в слово `"Pods"` для шапки.
- **`ScreenType(99)`** — намеренное **значение вне диапазона**. Экрана с номером
  99 не существует, поэтому это заставляет сработать ветку `default:` и вернуть
  `"Unknown"`. Это самая ценная строка в таблице — см. раздел 9.

## 6. Как запускать тесты

Из корня проекта:

```bash
go test ./...
```

`./...` означает «эта директория и все вложенные пакеты». Вывод при успехе
приятно немногословен — Go сообщает только о пакетах, где *есть* тесты:

```
ok      yak8sui/pkg/ui   0.309s
?       yak8sui/pkg/k8s  [no test files]
?       yak8sui/cmd/yak8sui  [no test files]
```

Для подробностей добавьте **`-v`** (verbose), чтобы видеть каждый подтест по
имени:

```bash
go test ./pkg/ui/ -v
```

```
=== RUN   TestScreenTypeString
=== RUN   TestScreenTypeString/pods_screen
=== RUN   TestScreenTypeString/deployments_screen
=== RUN   TestScreenTypeString/out-of-range_value
--- PASS: TestScreenTypeString (0.00s)
    --- PASS: TestScreenTypeString/pods_screen (0.00s)
    --- PASS: TestScreenTypeString/deployments_screen (0.00s)
    --- PASS: TestScreenTypeString/out-of-range_value (0.00s)
=== RUN   TestStatusColor
    ... (шесть подтестов) ...
--- PASS: TestStatusColor (0.00s)
PASS
ok      yak8sui/pkg/ui   0.309s
```

Обратите внимание: имена из `t.Run` становятся путями вроде
`TestStatusColor/pending_is_yellow` (пробелы превращаются в подчёркивания).
Именно это позволяет запустить **один** случай:

```bash
go test ./pkg/ui/ -v -run 'TestStatusColor/pending'
```

Флаг `-run` принимает регулярное выражение, сопоставляемое с путём теста, —
удобно, когда вы дорабатываете единственный падающий сценарий.

## 7. Как читать падение теста

Проходящие тесты скучны; настоящая ценность видна, когда что-то ломается.
Допустим, кто-то «упростил» `statusColor` и случайно сделал так, что `Pending`
проваливается в красный. Теперь запуск теста печатает:

```
=== RUN   TestStatusColor/pending_is_yellow
    colors_test.go:26: statusColor("Pending") = red, want yellow
--- FAIL: TestStatusColor/pending_is_yellow (0.00s)
...
FAIL
FAIL    yak8sui/pkg/ui   0.31s
```

Всё нужное — в одной строке:

- **`colors_test.go:26`** — точный файл и строка упавшего `t.Errorf`.
- **именованный подтест** `TestStatusColor/pending_is_yellow` говорит, *какой
  сценарий* сломался.
- **`= red, want yellow`** — паттерн `got, want` прямо показывает фактическое
  против ожидаемого. Вот почему порядок в
  `t.Errorf("... = %v, want %v", got, tc.want)` важен и является почти
  всеобщим соглашением в Go: **сначала фактическое, после `want` — ожидаемое**.
  Перепутаете местами — и каждое сообщение о провале будет врать.

Остальные пять строк всё равно отработали и прошли — один сломанный случай не
прячет остальные. Эта изоляция — прямая заслуга `t.Run`.

## 8. Зачем табличный стиль? В чём выгода

Можно было бы написать шесть отдельных функций `TestStatusColorRunning`,
`TestStatusColorPending`… Табличный стиль выигрывает по конкретным причинам:

- **Добавить случай — это одна строка.** В Kubernetes появилась новая фаза,
  которая вам важна? Допишите `{name: "...", status: "...", want: ...}` в срез.
  Никакой новой функции, никакого скопированного шаблона.
- **Логика проверки существует один раз.** Проверка `got != want` и её сообщение
  об ошибке живут в единственном месте. Исправили или улучшили сообщение раз —
  выиграли все случаи.
- **Случаи читаются как спецификация.** Любой может пробежать таблицу глазами и
  сразу увидеть весь контракт: «Running и Succeeded — зелёные, Pending —
  жёлтый, всё остальное — красное». Тест заодно служит документацией.
- **Единообразные, «грепаемые» падения.** Каждый случай падает одинаково,
  поэтому вывод предсказуем, а упавший сценарий назван.

Это *главный* паттерн тестирования в самой стандартной библиотеке Go — откройте
почти любой `_test.go` в исходниках Go, и вы найдёте `cases := []struct`.

## 9. Как выбирать хорошие случаи (ловушка ветки `default`)

Написать тест легко; написать *хорошие* случаи — это навык. Несколько принципов,
которые уже демонстрирует эта маленькая таблица:

- **Покрывайте каждую ветку.** У `statusColor` три исхода
  (зелёный/жёлтый/красный); каждый есть в таблице. `switch` с непокрытой веткой —
  это баг, ждущий своего часа.
- **Не забывайте `default`.** Легче всего оставить без теста именно
  «улавливающую всё» ветку `default:`. У обеих функций она есть, и обе
  задействованы — `statusColor("")` и `ScreenType(99)`. Случай `ScreenType(99)`
  особенно поучителен: в нормальном ходе программы такое значение *никогда* не
  возникнет (экраны только `ScreenPods` и `ScreenDeployments`), и всё же тест
  специально лезет в этот угол, чтобы доказать, что «страховочная сетка»
  работает.
- **Включайте граничные/краевые входы.** Пустая строка `""` — классический
  краевой случай для любой функции, принимающей `string`. Стоит одну строку, а
  ловит целую категорию багов «а что если пусто?».
- **Давайте каждой строке описательное `name`.** `"empty string is red"`
  говорит, что сломалось, не открывая файл. `"case6"` — нет.

> **О честности:** эти тесты проверяют *текущее, задокументированное поведение*.
> Они не доказывают, что поведение *желательно* — например, когда-нибудь вы
> захотите, чтобы неизвестная фаза пода была оранжевой, а не красной. И это
> нормально: тогда тест упадёт, вы прочитаете причину и осознанно обновите
> `want`. Упавший после намеренного изменения тест — это тест, делающий свою
> работу, а не помеха.

## 10. Честное ограничение: тесты-детекторы изменений

Теперь неудобная правда именно про `colors_test.go`: **как сеть для отлова багов
он слаб** — и стоит понять *почему*, потому что это ловушка, с которой вы будете
сталкиваться постоянно.

Поставьте код и тест рядом:

```go
// colors.go
case "Running", "Succeeded": return tcell.ColorGreen
// colors_test.go
{status: "Running", want: tcell.ColorGreen},
```

Тест — это **построчное зеркало реализации**. Он повторяет ровно то соответствие,
которое уже объявляет `switch`. Нет *независимого* способа прийти к ожидаемому
ответу — «оракул» теста это просто копия кода. Такой тест называют **тестом-
детектором изменений (change-detector test)** (или тавтологическим тестом), и у
него две слабости:

- **Он не поймает логическую ошибку, которую вы реально допустите.** Если вы
  намеренно поменяете соответствие, вы правите тест под него — поэтому он никогда
  не спросит «а вы *хотели* так сделать?». Он срабатывает только на *случайные*
  правки функции.
- **Код, который он охраняет, и так почти без багов.** `switch`, возвращающий
  константы, — один из самых низкорисковых кусков в репозитории, а неверный цвет
  — косметический дефект, который вы мгновенно заметите на экране, а не тихое
  повреждение данных. Низкая вероятность бага × низкая серьёзность = низкая
  страховая ценность.

Так что отношение пользы к самому факту существования здесь скромное. Тест дешёвый
(микросекунды, ~ноль обслуживания), но *дешёвый — не то же самое, что ценный*.

### Правило, которому это учит

Тест оправдывает себя, когда его ожидаемое значение вычисляется **иным путём**,
чем в тестируемом коде. Если тест просто отражает собственную логику реализации
обратно на неё, вы написали документацию, а не страховочную сетку. `app_test.go`
(`ScreenType.String()`) — из той же категории, тоже зеркало `switch`.

### Тогда зачем вообще их писать здесь?

Две честные причины, обе про *этот* проект, а не про промышленную надёжность:

1. **Обучение.** Это простейшие чистые функции, поэтому *механика* табличного
   теста (`[]struct`, `t.Run`, `got`/`want`) видна, и ничто ей не мешает. В этом
   и смысл руководства.
2. **Инфраструктура.** Они превращают шаг CI `go test` (раздел 11) из пустышки в
   нечто реальное, так что *следующему*, более ценному тесту есть где жить.

### Как выглядит тест, который действительно себя оправдывает

Сравните с логикой отношения готовности в `pkg/ui/deployments.go`:

```go
readyText := fmt.Sprintf("%d/%d", d.Available, d.Replicas)
```

Здесь тест писать стоит, потому что есть **реальный, правдоподобный баг**: два
операнда можно перепутать местами (`%d/%d` с `Replicas, Available`). Тест,
проверяющий, что `{Available: 3, Replicas: 5}` отрисовывается как `"3/5"` — такое
ожидание человек пишет независимо, зная нужный порядок, — поймал бы ошибку,
которую реально кто-то допустит. `colors_test.go` так не может никогда, потому что
там нет ни порядка, ни комбинации, ни вычисления, которое можно испортить. См.
шаг #1 в разделе 12 о том, как превратить эту логику в тест, который себя
оправдывает.

## 11. Как это встраивается в CI

Откройте `.github/workflows/ci.yml` — и увидите, что этот шаг уже там, он ждал:

```yaml
- name: Test
  run: go test ./...
```

До сих пор этот шаг запускался и не находил, что делать. С этими двумя файлами
**каждый push и pull request теперь реально проверяют логику цвета и имени
экрана на серверах GitHub.** Если будущее изменение сломает контракт из таблицы,
проверка CI станет красной *до* того, как код попадёт в основную ветку, — и для
этого не нужны ни кластер, ни терминал, потому что мы протестировали чистый слой.

Это и есть тихая награда за слоёную архитектуру из основного руководства: логика,
которую *можно* дёшево протестировать, теперь *и правда* тестируется —
автоматически, при каждом изменении.

## 12. Куда двигаться дальше

Эти два теста покрывают чистые функции. Естественное продолжение, примерно по
возрастанию сложности:

1. **Тестируйте больше чистой логики.** Экран деплойментов вычисляет отношение
   готовых/всего и выбирает зелёный или красный по условию `Available <
   Replicas`. Вынесите это решение в маленький чистый помощник (например,
   `deploymentReady(avail, total int32) bool`) и покройте его табличным тестом —
   приятное упражнение на «рефакторинг ради тестируемости».
2. **Введите интерфейс, чтобы тестировать «нечистый» код.** Функции вроде
   `k8s.ListPods` ходят в реальный кластер, поэтому их нельзя протестировать
   как есть. Стандартный ответ Go — определить небольшой **интерфейс**, от
   которого зависит UI, и передавать в тестах **фейковую** реализацию,
   возвращающую заранее заготовленные срезы `PodInfo` — без сети. Это тот самый
   концепт «интерфейсы + внедрение зависимостей», на который намекало основное
   руководство.
3. **Попробуйте `t.Parallel()`** внутри подтестов, чтобы запускать независимые
   случаи конкурентно — мягкое введение в конкурентность Go.
4. **Изучите `go test -cover`**, чтобы увидеть, какой процент кода выполняют
   тесты:
   ```bash
   go test ./... -cover
   ```
